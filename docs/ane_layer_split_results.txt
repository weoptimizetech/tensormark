ANE layer-split (fused segment) — measured verdict
====================================================
Date: 2026-09-11  (follows ane_numerics_gate.txt and the c2d508f blocker note)
Machine: M1, 8 GB unified memory, macOS 26
Model: TinyLlama-1.1B, real TMQ Q4_0 weights dequantized to fp16,
       S=1024-token prefill, numpy fp32 chain as reference.

Supersedes two earlier beliefs
------------------------------
1. "Fused single-graph ANE is blocked on coremltools blob-offset semantics"
   (c2d508f) — WRONG. A single-process ct.convert of a traced 22-layer torch
   module (weights streamed per-layer, ~88 MB peak extra) produces a
   coremltools-serialized package that loads and runs on ANE. The blob-offset
   problem only afflicts hand-packed weight.bin files.

2. "Chained ANE is ~151 ms/layer => fused ≈ 308 tok/s" (39ac1c2) — the 151 ms
   was ~85% per-predict dispatch overhead, not compute. Fused per-layer
   compute is ~29 ms.

The hard wall that IS real: ANE graph size
------------------------------------------
- fused 22-layer package: ANE compile fails (error code -14), reproducible
  with 14 GB free; N16 control compiled and ran fine at the same free memory.
  => hard M1 ANE compiler graph/weight-size limit, not resources.
- fp32 masked-softmax sandwich inside the graph also blocked ANE compile;
  bias-causal fp16 mask compiles (N8/N10/N12/N16 all OK).

The production shape: LAYER SPLIT
---------------------------------
fused ANE L0-15  ->  GPU L16-21  ->  fp32 lm_head
(/tmp/last6_gpu.mlpackage, ct-serialized, real weights)

  segment ANE  -> last6 GPU: top-1 vs fp32 ref 94.9%, rel RMS 1.09e-1
  segment CPU  -> last6 GPU: top-1 99.2%, rel RMS 1.6e-2  (control)

The fused segment is CLEANER than 22 chained predicts (2 serialization
points instead of 22): final top-1 94.9% BEATS the chained 92.5% despite the
segment's own 83.3% mid-graph agreement.

  wall: 462 ms (ANE seg) + 386 ms (last6 GPU package) = 848 ms @1024
      = 1208 tok/s  (+42% vs GPU-only 850 tok/s)

In-engine upside: the last6 GPU *package* costs 386 ms while the engine's own
GPU path runs ~29 ms/layer (~174 ms for 6 layers). If the engine ingests the
ANE hidden directly, the projected wall is ~636 ms ≈ 1610 tok/s (+89% vs
GPU-only) — this requires a hidden-state segment handoff in the engine and an
ESC-controller extension to a third unit (standing design goal).

Token-split concurrency is impossible for the fused segment (depth mismatch:
the GPU cannot start L16 before the ANE finishes L15). Layer-split is
sequential; the 1368 tok/s token-split sweep number does not compose with it.

Integration correction (2026-09-11)
-----------------------------------
The measurements above concern separate experimental CoreML packages, NOT a
validated in-engine prefill/decode integration. In particular, 2218 tok/s is
only the first 16 layers; it must not be compared directly to whole-engine
throughput. The serving goal remains independent-lane aggregate capacity,
not replacing or degrading the exact CPU/GPU lane.

The early bench_ane_split runs reporting 325-372 tok/s and exactly zero logit
difference did not establish ANE execution. The shim still required an output
named h at open, although hidden-only outputs retained their traced name.
The benchmark also set TM_ANE=0 AFTER model load, too late to disable an
already-open segment for its reference. Both issues are corrected; the
benchmark now requires its successful-ANE counter to advance in every round,
checks all logits for finiteness, and exits nonzero on setup refusal/fallback.
Its difference/top-1 metrics are observations, NOT a quality-equivalence gate.

The claim that explicit output renaming caused ANE inference error 0x16 was
premature: the unnamed-output package also failed direct CoreML prediction
(bg_160). Comparing with /tmp/ane_bias_build.py found a graph mismatch:
anepack used fp32 masked_fill + softmax, whereas the successful graph used
a finite fp16 additive causal bias (-30000) and fp16 softmax. The builder now
matches the latter. Its cache key includes builder source and config contents
to avoid reusing a package from a different graph revision. Model identity
still uses filename/size/mtime, not a full weight-content hash.

Other corrected integration contracts:
  - Source .mlpackage loading uses compileModelAtURL's returned URL.
  - Hidden output lookup supports an arbitrary single traced name; KV outputs
    remain explicitly named h/k_i/v_i, with shape (KVH,T,dh).
  - The shim checks fp16 types/shapes, respects MLMultiArray strides, rejects
    nonfinite outputs, and reports KV dimensions for engine buffer validation.
  - Fixed-position packages only run at cache base zero. They have neither
    past-K/V inputs nor position-offset inputs for chunked continuation.
  - Hidden-only K projection uses the per-head RoPE helper; calling rope_qk
    with a null query buffer was invalid and crashed the dispatch regression.

IMPORTANT: final hidden after layer K cannot reconstruct each earlier layer's
true K/V. Reprojecting all layers from it is a separate approximation, not
merely fp16 rounding. Hidden-only integration requires TM_ANE_APPROX_KV=1;
it is experimental, and must not be advertised as exact-cache inference or
used for unverified speculative-token acceptance. The KV-emitting path exports
the actual segment K/V, but large-shape ANE support must be tested separately.

Follow-up: double execution fixed (bg_168 / bg_169)
--------------------------------------------------
The successful-ANE counter was necessary but NOT sufficient: the final CPU
fallback tested only !gpu_stack_done. After ANE [0,K) plus tail [K,L) had
already completed, it ran the entire [0,L) stack again on that final hidden.
The old 46% drift and ~207 tok/s results therefore were not measurements of
the intended layer-split graph. Lower-layer approximate K/V cannot explain
initial-prefill logit drift: those cached rows are used by later continuation,
not by the already-computed prefix or different tail layers.

Added an exact fake-ANE oracle (engine block 0 + engine tail). It failed before
the fix with max logit difference 6.95373273; it passes afterward with 0.0.
The fallback now requires !ane_done && !gpu_stack_done. The extended regression
also checks exported actual K/V followed by decode, both with 0.0 maxdiff.
